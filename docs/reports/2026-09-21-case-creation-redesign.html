Case Creation Redesign

Block Customerless Cases

Date: September 21, 2026

Status: Ready for Manager Approval

Context: Follow-up to case-owner layer elimination (Sept 18-19). Addresses "ghost visibility" on cases created without a company.

Executive Summary

This redesign prevents cases from being created without a company, eliminating the "ghost visibility" where creators can see cases via a fallback rule. Instead, when someone creates a company, they explicitly choose their role (handler/assignee/neither), and that choice carries forward to any cases they create on that company.

Goals:
  • ✓ Every case always has clear, official ownership (audit/data integrity)
  • ✓ No creator-only "ghost visibility" loophole (access control)
  • ✓ Clear workflow: company → opt-in role → case (simplification)

Approaches Considered

✓ RECOMMENDED: Approach 1 — Strict Enforcement

How it works: Block case creation without company. When creating company, user opts in (handler/assignee/neither). That opt-in auto-applies to cases they create. Existing customerless cases must be assigned a company before use.

Pros:
  • Cleanest data integrity — every case always has official ownership
  • Eliminates "ghost visibility" loophole completely
  • Crystal-clear workflow: company → opt-in → case
  • Solves all three goals: audit, access control, simplification
Cons:
  • More restrictive UX — users can't create ad-hoc cases
  • Requires cleanup of existing customerless cases
  • If opt-in choice is wrong, must redo it
Approach 2 — Soft Enforcement with Wizard

How it works: Same blocking as Approach 1, but with a guided company-creation wizard explaining each role choice. Existing customerless cases get a soft nudge (banner), not forced migration.

Pros:
  • Same end state, but gentler UX
  • Educates users on role choices
  • Allows time for edge cases
Cons:
  • More UX complexity (wizard vs. simple form)
  • Deferred cleanup means ghost visibility persists temporarily
Approach 3 — Opt-Out Creator Fallback (Not Recommended)

How it works: Allow case creation without company. At company creation, default is "neither" (no fallback). Creator only sees case if they explicitly chose a role or are assigned ticket holder.

Pros:
  • Minimal UX friction
  • Backward compatible
Cons:
  • Doesn't solve ghost visibility — fallback still exists if users forget opt-in
  • Weaker audit trail
  • Doesn't achieve goal of "no orphaned cases"

Chosen Design: Approach 1 (Strict Enforcement)

Core Rules

Rule 1: Case Creation Gate

When someone tries to create a case, check if the target company exists.

  • If NO: Show floating timer message "Company needs to be created first" (5-4-3-2-1 countdown). User can click "Go now" to skip timer or "Cancel" to close.
  • If YES: Allow case creation normally.

Rule 2: Company Creation + Opt-In

When creating a company, prompt the creator to choose their role:

  • "Handler (Manager of this company's cases)" — you manage and own all cases
  • "Assignee (Ticket holder)" — you work on cases assigned to you, but don't manage them
  • "Neither (Just creating it for someone else)" — you're only involved if assigned a ticket

Store this choice. When the creator makes their first case, auto-apply their role choice.

Rule 3: Existing Customerless Cases

Query for any cases where customer_id is null. Before allowing view/edit, require company assignment:

  • Show modal: "This case has no company. Assign one before continuing."
  • User picks a company → case is re-linked → ownership recalculates

Rule 4: Handler Auto-Assignment

  • If user opted "handler" at company creation → auto-become handler of that company → own all its cases
  • If user opted "assignee" → NOT a handler; only see cases assigned to you
  • If user opted "neither" → only creator-fallback (see cases you created, if unmanaged account)
User Experience

Company Creation Flow

  1. User clicks "Create Company"
  2. Form appears: name, location, tags, etc.
  3. New section: "What's your role in this company?" (radio buttons for Handler/Assignee/Neither, with hints)
  4. User submits → company created + opt-in choice recorded
  5. Success screen: "View company" or "Create first case"

Case Creation Redirect Flow

  1. User clicks "Create Case" (no company selected)
  2. Floating message appears: "Company needs to be created first" (5-4-3-2-1 timer)
  3. Buttons: "Go to Create Company" | "Cancel"
  4. If timer reaches 0 and user does nothing → auto-redirect

Orphaned Case Assignment Flow

  1. User tries to view/edit case with no company
  2. Modal blocks: "This case has no company assigned"
  3. Dropdown: "Select a company..."
  4. User picks company → case re-links → case reloads with new ownership derived
Data & Database

Schema Changes

Table Change Why
companies Add creator_role_choice (enum: handler | assignee | neither) Store the creator's opt-in choice at company creation
cases customer_id becomes required non-null Every case must belong to a company; no orphaned cases
handlers None (auto-create handler row when user opts in) Handler assignments work as-is

Migration Plan

  1. Add creator_role_choice column to companies (nullable, default 'neither')
  2. Find all cases where customer_id is null (orphaned)
  3. For each orphaned case: create a data task for manual company assignment
  4. Add validation: prevent case creation if company doesn't exist
  5. Add UI gate: block view/edit of orphaned cases until assigned
Testing & Edge Cases

Test Scenarios

  1. L2 creates company as handler: L2 → handler → owns all cases ✓
  2. L2 creates company as assignee only: L2 → NOT handler, only visible via ticket assignment ✓
  3. L2 creates company as neither: L2 → creator-fallback only ✓
  4. Case creation blocked: Timer redirect works, user can cancel or go immediately ✓
  5. Orphaned case assignment: Modal forces company → ownership recalculates ✓
  6. All levels follow same rule: L3, L4, L5, L6 all need company first ✓
  7. Handler removal doesn't orphan: Case still belongs to company; ownership recalculates ✓

Edge Cases Handled

  • Editing customer_id to null: Blocked by validation — required non-null
  • Company deletion: Prevent if company has cases (or soft-delete only)
  • Change opt-in choice: Allow re-editing company to change role (handler ↔ assignee)
  • Multi-handler company, creator opted neither: Creator only sees via assignee; can't see if unassigned
  • Old companies without role choice: Treat as 'neither' (safest); allow admin update if needed
