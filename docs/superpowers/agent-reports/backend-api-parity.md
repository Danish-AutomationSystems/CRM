# Backend API parity report

Scope: legacy Google Apps Script server APIs in `docs/source-appscript/Code.gs`, cross-checked against `google.script.run` calls in `docs/source-appscript/Index.html` and behavior docs. All APIs re-identify the signed-in user via `me_()` unless noted. Return values are passed through `out_()`, so Dates become `yyyy-MM-dd` strings and row internals are stripped.

Parity summary: every client `gs('api_*')` call has a matching `function api_*` in `Code.gs`. The migration must preserve server-side auth; client state is never trusted.

## Access model to preserve

- `me_()`: active user must exist in `Users`; inactive or unknown users are rejected.
- Customer access: L4+ full access to all; handlers full access; L3 full access on matching tags and name-only outside; L2 name-only on matching tags and no access outside unless handler; L1 no customer browsing.
- Case visibility: L4+, case owners, assignee, or full customer access. Ticket assignee can see/work the case but does not receive full customer access.
- Writes to customer details, contacts, handlers, cases, and quotations generally require either explicit level gates or full customer/case visibility as listed below.

## Cross-cutting migration tests

- API parity: generated list of frontend `gs('api_*')` calls equals backend exported routes.
- Auth parity: every route rejects unknown/inactive users; all mutating routes ignore any client-supplied identity.
- Access matrix fixtures: L1/L2/L3/L4/L5/L6 with matching/nonmatching tags, handler/non-handler, case assignee, extra owner.
- Logging parity: every create/update/delete/status route writes the same `ActivityLog` action/entity/customer/details shape.
- Cache parity: customer mutations clear customer index; setting mutations clear settings cache; read routes do not mutate caches except normal cache population.
- ID/revision parity: concurrent customer/case/contact/quote creation allocates lock-protected sequential IDs; quote revisions supersede prior Draft/Sent rows.
- Data shape parity: migrated API responses use the same client-facing casing and array/object shapes, including `NAME` vs `FULL` customer payloads and minimal customer payload in `api_getCase`.
